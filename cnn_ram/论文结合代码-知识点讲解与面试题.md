## 1. 先用一句话讲清项目

### 1.1 最短版本

**背诵稿：**

这个项目本质上是一个 **Cortex-M0 + AHB/AHB-Lite + CNN 加速器** 的软硬协同 SoC，CPU 负责控制和通信，CNN 硬件负责做手写数字识别推理。

### 1.2 1 分钟版本

**背诵稿：**

[论文] 这个系统基于 Zynq-7020 平台，但没有使用 PS，而是在 PL 里自己搭了 Cortex-M0 软核、CNN 加速器、BRAM 和通信接口。系统通过 AHB-Lite 总线把 Cortex-M0、存储器和 CNN 外设连起来，上位机把 28×28 二值图像送进来，Cortex-M0 再通过总线把图像写入 CNN，加速器完成卷积、池化、全连接等计算后输出分类结果。

[代码] 从当前仓库能直接看到，`main.c` 会先向 CNN 数据寄存器写输入，再轮询结果寄存器；`CortexM0_SoC.v` 里 AHB_CNN 挂在 `HSEL_P5`，APB 子系统挂在 `HSEL_P4`；`cnn_top.v` 的链路是 `conv1 -> maxpool_relu -> conv2 -> maxpool_relu -> fully_connected -> comparator`。

[分析] 所以面试时可以把它讲成：**一个用 Cortex-M0 做控制、用 AHB 挂接 CNN 加速器的轻量 SoC 学习项目**。

## 2. 论文里是怎么描述这个系统的

## 2.1 平台与总体架构

- [论文] 平台是 **Zynq-7020 FPGA SoC**。
- [论文] **PS 不使用**，自定义逻辑都放在 **PL** 内实现。
- [论文] PL 中包含：
  - Cortex-M0 软核
  - CNN 加速器 IP
  - 双端口片上 BRAM
  - USIO 模块（UART/USB/JTAG 通信）
- [论文] 系统思路是“**软核处理器 + CNN 加速器协同工作**”：
  - Cortex-M0 负责控制、数据搬运、结果回传
  - CNN 加速器负责推理计算

### 2.2 论文中的 AHB-Lite 地址映射

[论文] 论文给出的地址映射如下：

| 地址范围 | 模块 | 说明 |
|---|---|---|
| `0x0000_0000 ~ 0x0001_FFFF` | AHB Flash | 指令存储，`WirelessMCU.hex` 初始化 |
| `0x2000_0000 ~ 0x2001_FFFF` | AHB SRAM | 数据存储 |
| `0x3000_0000 ~ 0x307F_FFFF` | AHB GPIO | GPIO 外设窗口 |
| `0x3080_0000 ~ 0x30FF_FFFF` | DMA | DMA 寄存器空间 |
| `0x4000_0000 ~ 0x4FFF_FFFF` | AHB-to-APB | UART/Timer 等低速外设 |
| `0x6000_0000 ~ 0x6FFF_FFFF` | CNN | CNN 控制空间 |

### 2.3 论文中的 CNN 寄存器接口

[论文] 论文描述 CNN 加速器有 **4 个 32 位寄存器**：

- `DATA`：写入输入像素
- `ADDR_WE`：BRAM 地址与写使能配置
- `CTRL`：启动与清零
- `STATUS`：返回结果

### 2.4 论文中的运行流程

[论文] 论文中的运行流程可以概括为：

1. 上位机发送预处理后的 `28×28` 二值图像
2. Cortex-M0 通过 AHB 总线把图像写入 CNN 输入缓存
3. CNN 做“卷积 → 池化 → 卷积 → 池化 → 全连接”计算
4. 结果写回片上存储
5. Cortex-M0 读出结果并通过串口回传上位机

### 2.5 论文中的 CNN 结构与指标

[论文] 网络结构：

- 输入：`28×28×1`
- 第一卷积层：`5×5, stride=1`，输出 `24×24×3`
- 第一池化层 + ReLU：`2×2, stride=2`，输出 `12×12×3`
- 第二卷积层：`5×5, stride=1`，输出 `8×8×3`
- 第二池化层 + ReLU：`2×2, stride=2`，输出 `4×4×3`
- 全连接层：`48 -> 10`

[论文] 参数量与乘加估算：

- 第一卷积层：参数 `78`，乘加 `43,200`
- 第二卷积层：参数 `228`，乘加 `14,400`
- 全连接层：参数 `490`，乘加 `480`
- 总计：参数 `796`，乘加 `58,080`

### 2.6 论文中的性能与资源数据

[论文] 论文摘要给出的关键指标：

- 时钟频率：`50MHz`
- 平均识别时间：`13μs`
- 准确率：`91%`

[论文] 资源占用表给出的关键数据：

| 资源 | 使用量 | 可用量 | 利用率 |
|---|---:|---:|---:|
| LUT | 36708 | 53200 | 69.00% |
| LUTRAM | 72 | 17400 | 0.41% |
| 寄存器 | 8375 | 106400 | 7.87% |
| BRAM | 32 | 140 | 22.86% |
| DSP | 3 | 220 | 1.36% |
| IO | 10 | 125 | 8.00% |
| BUFG | 2 | 32 | 6.25% |

## 3. 当前仓库里能直接看到什么

这部分只说当前仓库源码里能直接读出来的内容。

### 3.1 软件侧：`main.c`

文件：`cnn_ram/Keil/Keil_proj/USER/main.c`

[代码] 可以直接看到：

- 定义了：
  - `CNN_DATA_REG = (CNN_BASE_ADDR + 0x0)`
  - `CNN_RESULT_REG = (CNN_BASE_ADDR + 0x4)`
- `main()` 里先调用：
  - `SystemInit()`
  - `UartInit()`
  - `GpioInit()`
- 然后把 `test_03_buf[784]` 中的像素逐个写入 `CNN_DATA_REG`
- 随后轮询 `CNN_RESULT_REG`
- 如果 `read_data & 0x100` 成立，就打印 `read_data & 0xF`

**可直接提炼的结论：**

- [代码] 软件不是调用某个 `cnn_run()` 函数，而是通过 **固定地址寄存器读写** 驱动 CNN。
- [代码] 当前软件可观察接口至少包括：
  - `+0x0`：输入数据入口
  - `+0x4`：结果读取入口

### 3.2 SoC 顶层：`CortexM0_SoC.v`

文件：`cnn_ram/Vivado/CM0_Proj/CM0_Proj.srcs/sources_1/imports/new_rtl/CortexM0_SoC.v`

[代码] 可以直接看到：

- 顶层实例化了 `cortexm0ds_logic`，说明系统中确实有 Cortex-M0 软核。
- APB 子系统实例 `cmsdk_apb_subsystem` 接在 `HSEL_P4`。
- CNN 外设实例 `AHB_CNN`（`cmsdk_ahb_eg_slave`）接在 `HSEL_P5`。
- UART 通过 APB 子系统对外连出：
  - `uart0_rxd -> RXD`
  - `uart0_txd -> TXD`

**可直接提炼的结论：**

- [代码] CNN 是 **AHB 上的从设备**，不是直接点对点连 CPU。
- [代码] UART 属于 **APB 侧低速外设**。
- [代码] 整个系统是典型的：**AHB 主干 + AHB-to-APB 外设支路**。

### 3.3 AHB slave 接口层：`cmsdk_ahb_eg_slave_interface.v`

文件：`cnn_ram/Vivado/CM0_Proj/CM0_Proj.srcs/sources_1/imports/sources_1/imports/verilog/cmsdk_ahb_eg_slave_interface.v`

[代码] 这里最关键的一句是：

```verilog
wire trans_req = hreadys & hsels & htranss[1];
```

这说明当前 AHB slave 认定“有效访问”的条件是：

- `hreadys = 1`：总线允许推进
- `hsels = 1`：当前 slave 被选中
- `htranss[1] = 1`：当前传输类型有效（通常对应 `NONSEQ/SEQ`）

[代码] 这个模块还做了两件工程上非常关键的事：

- 把地址寄存下来 `addr_reg <= haddrs[...]`
- 把 `HSIZE + HADDR` 翻译成 `byte_strobe`

**可直接提炼的结论：**

- [代码] 这是一个标准的 **AHB-Lite 协议翻译层**。
- [代码] 它的作用不是做 CNN 运算，而是把复杂总线协议翻成简单寄存器接口：
  - `addr`
  - `read_en`
  - `write_en`
  - `byte_strobe`
  - `wdata`

### 3.4 寄存器层：`cmsdk_ahb_eg_slave_reg.v`

文件：`cnn_ram/Vivado/CM0_Proj/CM0_Proj.srcs/sources_1/imports/sources_1/imports/verilog/cmsdk_ahb_eg_slave_reg.v`

[代码] 这个模块里有 4 个数据寄存器：

- `data0`
- `data1`
- `data2`
- `data3`

但**从当前可观察连线看**，真正接到 CNN 输入/输出语义上的主要是：

- `data0`：输入寄存器
  - `data0[7:0] -> cnn_data_in`
  - `data0[8] -> cnn_data_valid`
- `data1`：结果寄存器
  - `data1 <= {23'd0, 1'b1, 4'd0, cnn_decision}` 当 `cnn_result_valid` 时更新

[代码] 这意味着当前仓库可直接确认的最小寄存器语义是：

- `+0x00`：输入像素与输入有效位
- `+0x04`：结果有效位与分类结果

`data2/data3` 虽然存在，但从当前已读代码中**还不能直接证明**它们已经对应论文里的 `ADDR_WE/CTRL` 语义。

### 3.5 CNN 顶层：`cnn_top.v`

文件：`cnn_ram/Vivado/CM0_Proj/CM0_Proj.srcs/sources_1/imports/sources_1/new/cnn_top.v`

[代码] 当前仓库中 CNN 数据链路是明确的：

  -> maxpool_relu_1
  -> conv2_layer
  -> maxpool_relu_2

其中：

- 输入：`cnn_data_in`、`cnn_data_valid`

**可直接提炼的结论：**

- [代码] 当前仓库里的 CNN 是标准的“卷积 / 池化 / 全连接 / 比较输出类别”链路。

## 5. 核心知识点讲解

## 5.1 为什么这算一个 SoC，而不只是一个 CNN 模块？

[分析] 因为它不是“单个 RTL 算法模块”，而是把以下部件组织成了一个完整系统：

- CPU：Cortex-M0
- 主干总线：AHB/AHB-Lite
- 低速外设支路：APB
- 存储：Flash / SRAM / BRAM
- 算法加速器：CNN
- 通信接口：UART

面试里如果被问“你做的是模块还是系统”，可以答：

> 我做的不是单个卷积模块，而是一个带 CPU、总线、外设和加速器的轻量 SoC，CNN 只是其中一个 memory-mapped 外设。

## 5.2 什么是 memory-mapped I/O？

[分析] memory-mapped I/O 的本质是：

- 把外设寄存器映射到 CPU 的地址空间里
- CPU 像访问内存一样访问外设
- 真正完成访问的是“地址译码 + 总线路由 + 寄存器接口”

结合本项目：

- [代码] `main.c` 不是调用某个软件函数，而是写 `CNN_DATA_REG`
- [代码] 然后读 `CNN_RESULT_REG`

所以面试中可以说：

> CNN 在这个系统里不是函数调用对象，而是一个带寄存器接口的硬件外设。

## 5.3 为什么 CNN 适合挂在 AHB，而不是 APB？

[分析] AHB/AHB-Lite 更适合作为主干总线，原因是：

- 面向高性能访问
- 支持更复杂的传输时序
- 更适合连接 CPU、存储器和高速外设

APB 更适合：

- UART
- Timer
- Watchdog
- 简单寄存器类外设

结合本项目：

- [代码] `AHB_CNN` 在 `HSEL_P5`
- [代码] APB 子系统在 `HSEL_P4`

所以可以说：

> 这个项目里 AHB 是主干，CNN 这种需要连续喂数据的加速器挂在 AHB 上更合理；UART 这种低速外设挂在 APB 上更合理。

## 5.4 `trans_req = hreadys & hsels & htranss[1]` 为什么重要？

[分析] 这是一个非常典型的 AHB-Lite 有效访问判定条件。

它表示：

- 总线允许推进
- 当前 slave 被选中
- 当前传输类型有效

为什么它重要？

- 可以避免在 `IDLE/BUSY` 这类非有效状态误触发寄存器更新
- 体现你理解 AHB 不是“只要选中就一定在传数据”

面试被问到 AHB 有效访问时，可以直接说：

> 我项目里示例 slave 就是用 `HREADY & HSEL & HTRANS[1]` 作为有效请求入口的，这说明我不是只背概念，而是结合接口代码理解过时序。

## 5.5 为什么地址和 `byte_strobe` 要寄存？

[分析] 因为 AHB 的关键特点是：

- 地址阶段和数据阶段分离
- 当前这拍可能在处理上一笔数据阶段，同时准备下一笔地址阶段

所以：

- 地址不能直接一路组合地给后级
- `HSIZE/HADDR` 算出来的字节写使能也需要跟着访问阶段对齐

这类问题常用来区分“只知道总线名字”和“真正理解总线两阶段时序”的候选人。

## 5.6 这套 CNN 硬件链路是怎么工作的？

结合论文和代码，可以这样讲：

1. [论文] 输入是 `28×28×1` 的二值图像
2. [代码] `conv1_layer` 提取第一层特征
3. [代码] `maxpool_relu_1` 做第一次池化和激活
4. [代码] `conv2_layer` 做第二层卷积
5. [代码] `maxpool_relu_2` 做第二次池化和激活
6. [代码] `fully_connected` 输出分类分数
7. [代码] `comparator` 选择最终 `decision`

面试里不要只说“用了 CNN”，而要能说出：

- 这是 **两级卷积 + 两级池化/ReLU + 全连接 + 比较器**
- 数据在流水线上逐级传播
- 有 `valid_out_x` 这类信号辅助各级时序对齐

## 5.7 为什么论文强调低 DSP 占用？

[论文] 论文给出的 DSP 占用仅为 `3 / 220`，很低。

[分析] 这背后的工程动机通常有三点：

1. 板卡资源有限，DSP 是稀缺资源
2. 把更多乘加和控制逻辑摊到 LUT/BRAM，有助于给后续扩展留空间
3. 对轻量 CNN 而言，适当牺牲部分结构豪华度，换取更高可实现性是合理的

面试时可以这样说：

> 这个项目不是一味堆算力，而是更强调在中小资源 FPGA 上把轻量网络跑起来，所以从论文表述看，它在网络压缩和 DSP 节省上做了明显取舍。

## 5.8 为什么论文里会出现“13μs”和“毫秒级”两种说法？

[论文] 摘要写的是平均识别时间 `13μs`。

[论文] 但正文运行流程部分又写了“毫秒级”。

[分析] 这说明论文里存在表述不完全一致的地方。面试时更稳妥的说法是：

> 论文摘要报告的核心数据是 50MHz 下平均识别时间 13μs、准确率 91%；正文里还有“毫秒级”的表述，因此我会把 13μs 明确表述为论文报告结果，而不会说这是我在当前仓库里重新复测出来的数据。

这类回答既不回避问题，也不会显得你在硬拗。

## 5.9 论文中的四寄存器模型，当前代码为什么不能直接等同？

[论文] 论文讲的是更完整的控制面模型：`DATA/ADDR_WE/CTRL/STATUS`。

[代码] 当前已读代码里可直接确认的是：

- `data0`：输入数据与输入有效
- `data1`：结果与结果有效
- `data2/data3`：存在，但当前尚未直接看到与 CNN 控制链路的完整绑定

[分析] 这说明：

- 论文表达的是较完整的系统接口设计思路

## 6. 怎么把这个项目讲得像“自己真的做过”

## 6.1 30 秒版本

> 这是一个基于 FPGA 的轻量 SoC 数字识别系统。我在 PL 里放了 Cortex-M0 软核和 CNN 加速器，CPU 通过 AHB/AHB-Lite 把输入图像写到 CNN 外设，再读回分类结果，通过 UART 回传。项目重点不是单个卷积模块，而是把 CPU、总线、加速器和外设组织成一个能跑通闭环的系统。

## 6.2 1 分钟版本

> 从论文角度，这个系统基于 Zynq-7020，但没有用 PS，而是在 PL 里搭 Cortex-M0、CNN、BRAM 和通信接口，走的是轻量 SoC 架构。总线主干是 AHB-Lite，CNN 挂成 memory-mapped 外设。当前仓库里也能看到这一点：顶层把 CNN 放在 `HSEL_P5`，APB 外设放在 `HSEL_P4`，软件侧通过 `CNN_DATA_REG` 写 784 个像素，再轮询 `CNN_RESULT_REG` 拿结果。CNN 链路本身是两层卷积、两层池化/ReLU、全连接和比较器。面试时我会重点讲三件事：为什么这是 SoC、为什么 CNN 要挂 AHB、以及论文接口设计和当前代码实现之间有哪些对应与差异。

## 6.3 2 分钟版本

> 这个项目本质上是一个软硬协同的数字识别 SoC。论文里采用的是 Zynq-7020 平台，但不使用 PS，而是在 PL 中自己构建 Cortex-M0 软核、CNN 加速器、BRAM 和通信模块。系统通过 AHB-Lite 总线矩阵把 Flash、SRAM、GPIO、DMA、APB 子系统和 CNN 连接起来。CNN 不是函数，而是一个 memory-mapped 的 AHB 外设。当前仓库里，`main.c` 可以看到软件会把一张 `28×28` 图像逐像素写入 `CNN_DATA_REG`，之后轮询 `CNN_RESULT_REG`，当有效位拉高后读出低 4 位分类结果。硬件顶层中，CNN 是 `AHB_CNN`，挂在 `HSEL_P5`；APB 子系统挂在 `HSEL_P4`。AHB slave 接口层把 `HADDR/HTRANS/HWRITE/HSIZE` 等协议翻成简单寄存器读写接口，关键入口是 `trans_req = hreadys & hsels & htranss[1]`。CNN 本身的数据通路是 `conv1 -> maxpool_relu -> conv2 -> maxpool_relu -> fully_connected -> comparator`。论文报告的结果是 50MHz、91% 准确率、13 微秒平均识别时间，以及非常低的 DSP 占用。需要注意的是，论文里描述了更完整的四寄存器控制面，而当前仓库能直接确认的主要是输入寄存器和结果寄存器闭环，所以面试时我会主动把论文设计意图和代码现状区分开来讲。

## 7. 面试题归纳（附答题要点）

## 7.1 架构与 SoC 方向

### 题 1：这个项目为什么算 SoC，而不是单个 CNN 模块？

**答题要点：**

- 有 CPU（Cortex-M0）
- 有主干总线（AHB/AHB-Lite）
- 有低速外设支路（APB/UART）
- 有存储、外设、加速器协同

**推荐回答：**

> 因为它不是单个算法 RTL，而是把 Cortex-M0、总线、存储器、UART 和 CNN 加速器整合在一起，形成了一个能完成“输入 → 推理 → 回传”的完整片上系统。

### 题 2：为什么论文说是 Zynq-7020，但又用了 Cortex-M0？

**答题要点：**

- 平台是 Zynq-7020 板卡/FPGA 资源
- 但系统控制核心不是走 PS ARM
- 而是在 PL 里自建 Cortex-M0 软核

**推荐回答：**

> 这里的重点不是依赖 Zynq 自带的 PS，而是利用 Zynq 的 FPGA 资源在 PL 内构建一个自定义 SoC。也就是说，Zynq 在这里更多是承载平台，而不是直接拿 PS 作为控制核心。

### 题 3：为什么不用纯软件跑 CNN？

**答题要点：**

- CNN 有大量卷积乘加
- FPGA 并行性更强
- 功耗和可定制性更适合边缘场景

**推荐回答：**

> 纯软件跑 CNN 灵活，但在嵌入式场景下延时和功耗不占优。这个项目的思路是让软件负责控制和通信，让硬件负责并行计算，这样效率更高。

## 7.2 AHB / AHB-Lite / memory-mapped I/O 方向

### 题 4：为什么 CPU 写一个地址就能驱动 CNN？

**答题要点：**

- CNN 是 memory-mapped 外设
- CPU 发起的是总线访问
- Bus Matrix / 地址译码会把请求路由到 CNN slave

**推荐回答：**

> 因为 CNN 在系统里不是函数，而是地址空间里的一个 AHB 外设。CPU 对固定地址发起写访问，经过总线路由后，CNN 外设寄存器就能收到对应数据。

### 题 5：这个项目里为什么 CNN 挂在 AHB，不挂在 APB？

**答题要点：**

- AHB 是主干总线
- 更适合 CPU、存储器、高速外设
- APB 更适合 UART/Timer 这类低速寄存器型外设

**推荐回答：**

> CNN 需要连续接收图像输入、参与更高频的数据交互，所以更适合挂在 AHB 主干上；UART 这种简单控制型外设放在 APB 更合理。

### 题 6：`trans_req = hreadys & hsels & htranss[1]` 说明了什么？

**答题要点：**

- 这是 AHB-Lite 有效访问判定条件
- `HREADY` 表示总线可推进
- `HSEL` 表示 slave 被选中
- `HTRANS[1]` 表示传输类型有效

**推荐回答：**

> 这说明我理解的不只是“总线名字”，而是有效访问到底在什么条件下成立。这个条件避免了 IDLE/BUSY 误触发，也体现了 AHB-Lite 时序的关键点。

### 题 7：为什么 AHB slave 里要寄存地址和 `byte_strobe`？

**答题要点：**

- AHB 地址阶段和数据阶段分离
- 当前拍地址可能已经切到下一笔访问
- 所以后级寄存器逻辑要使用锁存后的地址和字节写使能

**推荐回答：**

> 因为 AHB 是流水化总线，地址和数据不在同一拍完成。如果不把地址先锁存，到了数据阶段就可能已经不是同一笔访问的地址了。

## 7.3 CNN 硬件实现方向

### 题 8：这个 CNN 的硬件链路是怎样的？

**答题要点：**

- `conv1_layer`
- `maxpool_relu_1`
- `conv2_layer`
- `maxpool_relu_2`
- `fully_connected`
- `comparator`

**推荐回答：**

> 当前仓库里 `cnn_top.v` 很清楚地给出了这条链路。前面两级做卷积和池化/ReLU，后面全连接输出分数，最后比较器给出分类结果。

### 题 9：为什么论文里强调行缓冲和滑动窗口？

**答题要点：**

- 5×5 卷积需要连续获得 25 个相邻像素
- 行缓冲可以把串行输入重组成局部窗口
- 这是卷积层硬件实现的典型做法

**推荐回答：**

> 卷积不是简单拿一个点做乘法，而是要拿一个局部邻域。行缓冲的作用就是把流式输入变成可并行计算的 5×5 窗口，这是硬件卷积实现的关键基础设施。

### 题 10：为什么 ReLU 在 FPGA 上容易实现？

**答题要点：**

- 本质是比较和选择
- 不需要复杂乘法
- 可用符号位判断、MUX 输出 0 或原值

**推荐回答：**

> ReLU 对硬件非常友好，因为它本质就是 `x>0 ? x : 0`，通常用符号检测和多路选择器就可以实现，不需要额外 DSP。

### 题 11：为什么论文里 DSP 用得这么少？

**答题要点：**

- 网络做了轻量化
- 算法和硬件实现做了资源取舍
- 重点是“在资源受限 FPGA 上可实现”

**推荐回答：**

> 这个项目不是追求极限精度，而是追求在中等资源平台上把 SoC + CNN 整体跑通，所以论文会特别强调 LUT/BRAM 为主、DSP 很省的实现策略。
